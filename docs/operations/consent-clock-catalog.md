# Consent migrations in the scheduling clock census

Comparison: wave base `4f8d2454` to lane `8ac44f20`. A single clean-base run of the 133 scheduling probes passed; the same probes failed on the uncorrected lane. Catalog snapshots at **each** migration-changing commit distinguish when a schema object was created from when scheduling could first reach it. No difference was attributed solely to comparing the lane with its own R7 predecessor.

The snapshots found 78 additional reachable nodes and 48 changed nodes. Of the 126, **105 already existed** at the wave base. An advisory-lock overload or a PostgreSQL aggregate was not created by F5: it entered this census through an F5 dependency. The persisted catalog had 39 changed or added definitions across functions, policies and columns. There were no new relation or type definitions in that physical diff.

The four newly reached PostgreSQL functions remain opaque. Each exact signature, implementation, language, extension, library, return type and volatility is pinned separately in `tests/scheduling/clock_opaque_allowlist.json`; removing a single entry makes both the opaque-review and full graph assertions fail. No routine pattern or exemption is used.

The 0023 migration compares the complete policy text generated by the source database against its reviewed digest before issuing static DDL. In `ai_pending_visible(text, uuid)`, the deployed definition differs only by removal of 13 redundant `::text` casts on literal setting names (11 tenant and two user lookups). Its `statement_timestamp()` marker remains. The 0026 migration checks the existing function’s fingerprint and applies that same definition in place; an unknown preimage aborts rather than overwriting drift. Neither migration permits a dynamically constructed setting name.

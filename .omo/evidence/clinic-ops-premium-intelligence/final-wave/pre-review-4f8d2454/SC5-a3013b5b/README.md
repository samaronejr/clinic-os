# R4e — how to verify this evidence

`junit.xml` is the native result of the single serial, non-browser SC-5 invocation. Its suite name includes the product SHA and systemd invocation. `reference.txt` comes from separate collection: all 16,651 previous public node IDs must remain, and the 14 additions must have the declared static addresses. Parameter suffixes are replaced with the SHA-256 of the full original ID. `sc5_report.py` preserves nonpassing result tags and records actual lifecycle phases while removing output, properties and free-form error text. `verify.py` rebuilds the five-field manifest from JUnit, checks every ID, native duration and setup/call/teardown against `phases.json.gz`, and compares every byte. No supplemental or historical invocation supplies a row.

Replay from this directory (`<SHA>` is the product, not the evidence commit):

```
python -I -B verify.py
sha256sum --strict --check SHA256SUMS
python -I -B validate_aux.py . <SHA>
python -I -B validate_handoff.py . <SHA>
python -I -B validate_controls.py mutations.json mutation.xml <SHA>
python -I -B validate_pidfd_rejection.py .
python -I -B validate_pidfd_rejection.py . --full
python -I -B validate_native_race.py .
```

From a repository containing the product commit, run `python -I -B <dir>/validate_origins.py <dir>/catalog-origins.json <SHA>`. The validator reads the committed policy blob and the migration paths from Git, not from a deployed database.

**Rejected invocation on this same product.** `6e314fbb752c431f8312eca63f688966` exited 1: 16,654 passed, 10 call failures, two phase errors; 11 distinct affected IDs out of 16,665. One ID both failed its call and errored during teardown. Its frozen JUnit, phases, unit result and attribution have the `rejected-pidfd-` prefix. The uv-managed Python 3.12.12 build had no native `os.pidfd_open`; the supervisor's failed cleanup led to child-resource warnings, including in the next fixture. The release chain exited 1 without pushing. Selecting system CPython 3.12.3, proving a real kernel pidfd and syncing the **same** lockfile fixed that precondition without a mock, product edit, skip, or weakened assertion. All 11 affected IDs passed separately (`pidfd-control.xml`). The corrected full invocation reran the entire identical reference from scratch, with a fresh coverage data file; neither the rejected invocation nor this targeted preflight supplies any row to its manifest.

**Second rejection and resource controls.** The first native-pidfd full invocation, `71d05494cece40ecb1c455a426bf98ba`, cleared all 11 affected IDs. It failed only the cross-clinic lifecycle race: the consumer did not observe both committed OTP decisions before its unchanged ten-second wait elapsed. This was before the test released the shared canonical-email gate, not a failed duplicate-identity assertion. The test and identity implementation are unchanged from r4d. This red receipt did not record CPU throttling, database waits, or child stacks; it does not prove a particular historical cause. The owned cluster log had no reported lock timeout or deadlock in the test window. `rejected-race-*` preserves its evidence. On the release SHA we measured the unmodified test under a quarter-core quota and again uncapped, with all 26 coverage targets and actual subprocess tracing enabled. The global DB-lane flock now serializes cooperating lanes; compile caches were primed in the locked venv and checkout. The certifying full run is uncapped and niced to 10; `serial-budget.json` witnesses lock identity and a genuinely refused concurrent acquisition. Cgroup counter deltas, the separate results and the timing of the same case within SC-5 are independently replayable. No saved rows from either rejected full run or either resource control can enter the certifying manifest.

**Authority.** PostgreSQL supplies the explicit role graph and the local database-owner edge. Runtime ownership of a namespace is an additional independent denial; it does not itself give PostgreSQL membership in `pg_database_owner`. Bare-owner controls use a secondary database with no restricted local grant; a suffixed machine with no staff membership isolates the machine-root omission. The old delegated-routine property is still checked both by PostgreSQL's privilege inquiry and by the separate routine oracle while the owner is reachable. The full gate additionally refuses bare reachability. No files, memory dumps, or privileged native routines were accessed by the grant tests.

**Policy provenance.** `run_origins.py` and `catalog_origins_exact.py` ran on a fresh independent private PG16 cluster from an empty database, not the suite database. At each committed migration a second connection observed OIDs, exact `regprocedure` signatures, `pg_get_function_identity_arguments`, definitions (only their hashes are retained), owners and ACLs. For each surviving OID the witness distinguishes its first creation, last naming/identity change and final definition change. The two argument representations prevent conflating overloads, argument types or modes. The verifier never learns permissions at runtime. `catalog-origins.json` records no DDL body, URLs, credentials or patient values. `validate_origins.py` reconciles every final signature, owner, digest, ordinary grantee, grant option and migration citation.

**Diagnostics.** `focused.json` and `focused.xml` are the positive run. All seven end-to-end cases contain real positive/refusal/recovery verdicts, including repeated refusals when the owner remains reachable. The schema-ownership, delegation, default-PUBLIC and private overload tests run against real catalogs. `recorder.json` and `recorder.xml` are separate fault controls: each extra recorder row was independently visible after commit and failed the original live set comparison. The protected graph's leaves are explicitly reinstalled, and the check precedes disposal of the clone. `mutations.json` and `mutation.xml` separately identify the call-phase assertion for each of 38 omissions. Stock monitoring-role overlaps are removed *only inside rolled-back tests* so that the component checks can be falsified independently. The sole equivalent omission is explicit `rolsuper` on PG16; the denial test remains. The original preflight for machine-only ownership still failed closed when the canonical role arm independently saw it. The released diagnostic uses the isolated suffixed login instead; it neither combines invocations nor disables that production check.

**Handoff.** `handoff.json` is copied from the real test report by `handoff_witness.py`, not reconstructed from elapsed suite totals. It covers the prior populated mode-migration rehearsal and clone teardown, an idle interval on the same warmed lease during the independent fresh control, a real Make/uv/verifier on the same cluster, and a deliberately stalled test-only launcher with an owned descendant. Only stage/ordinal/timing, readiness and identity comparison verdicts, sanitized process counters, and aggregated backend states, transaction ages, waits and blocked counts are retained. No query, process arguments, database IDs, server IDs, secrets or input values are kept. The controlled stall must reach 15 seconds, be located before verifier startup, and leave no group or backend behind. The two real probes must finish **within** 15 seconds. An individual trace locates the observed stage/state, not necessarily an unobservable historical OS root cause.

`gate-summary.json` and `run.json` bind SHA, unit and invocation, component validators and exit codes. `gate-exits.json` retains each pytest summary line, distinguishes expected nonzero diagnostics from validator exits, and includes all three full systemd exits. The separate 3,308-case isolation JUnit contains exactly the isolation subset of the complete run, including six restore guards. The main disposable PG instance alone ran with fsync off. This is local synthetic verification, not independent review, hosted CI, a production rollout or a live restore.
